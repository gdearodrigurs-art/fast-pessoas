## Recrutamento & Seleção e admissão digital

### Gupy (Recrutamento & Seleção + Gupy Admissão) — veredito: incorporar · verificação: parcial

**O que faz:** ATS líder no Brasil (vagas, candidaturas, página de carreiras) + módulo Gupy Admissão: admissão digital por etapas com coleta de dados pessoais, upload e validação de documentos do pré-colaborador, assinatura de contrato e movimentação entre etapas (SEND_DOCUMENTS, SIGNING_CONTRACT, ADMISSION_CONCLUDED, OUT_PROCESS).

**API:** SIM, pública e a mais bem documentada da categoria (developers.gupy.io). REST/JSON, autenticação por Bearer Token gerado nas configurações avançadas da plataforma (com escopos por endpoint; o fluxo de webhook exige permissão 'Webhook Configurations' V1). API Reference cobre: Applications (listar/criar/mover candidaturas, tags), Jobs (criar/listar/atualizar/fechar vagas), Career Pages, Departments, Job Custom Fields, Job Templates, Job Roles, Company Users, Branches, Post Hiring e Webhooks. FLUXO DE ADMISSÃO PARA FOLHA documentado passo a passo: 1) registrar webhook via POST /api/v1/webhooks com action='pre-employee.moved', postbackUrl (HTTPS público do middleware), status='active', techOwnerName/Email e clientHeaders opcionais; 2) filtrar a etapa de interesse por body.data.admission.status; 3) payload já traz candidato (nome, email, telefone, nascimento, endereço), vaga (job.code, department, role, branch), application e o array admission.documents.preEmployee com documentos preenchidos (RG, CPF, CNH, dados bancários, dependentes etc.); 4) entrega at-least-once — deduplicar pelo campo id. Há ainda fluxo separado de Download de Documentos de Admissão via API (disparo na etapa Admissão Concluída; .zip com cópias em PDF/JPEG + .TXT com dados transcritos; links com expiração configurável até 12h). Expõe também llms.txt e OpenAPI para agentes.

**Webhooks:** SIM, núcleo da integração: pre-employee.moved (dispara a CADA movimentação do pré-colaborador entre etapas do Gupy Admissão) + webhooks de recrutamento/notificações. Configuração self-service via API, garantia at-least-once, guias de teste com payloads reais. É exatamente o mecanismo para o admitido 'cair' no nosso núcleo de colaborador: pre-employee.moved (status ADMISSION_CONCLUDED) -> middleware próprio (FastAPI ou n8n) -> POST no nosso módulo de colaborador.

**Preço:** Sem preço público no site oficial (venda consultiva, demonstração). Terceiros (Betterteam/Capterra) citam planos a partir de ~R$730/mês em contrato anual — NÃO confirmado em fonte primária. R&S e Admissão são módulos contratados separadamente.

**LGPD/eSocial:** A doc técnica de developers NÃO menciona eSocial explicitamente; os templates de admissão são configuráveis e a própria doc alerta que 'a integração NÃO GARANTE que todos os dados enviados serão os necessários para concluir uma admissão no sistema de folha' — o DE/PARA para Nasajon/eSocial é responsabilidade nossa (a Gupy tem integrações padronizadas prontas com Metadados, Protheus e Sênior; Nasajon não aparece na lista, reforçando o caminho via webhook custom). Payload do webhook carrega dados pessoais e documentos — exigir DPA e tratar como dado pessoal sob LGPD no nosso lado (a doc recomenda testes em produção com CPFs válidos, o que pede cuidado com dados reais).

**Justificativa do veredito:** O fluxo que queremos existe e é oficialmente documentado ponta a ponta: webhook pre-employee.moved com payload completo do admitido (incl. documentos) + API de download de documentos. Dá para o admitido cair direto no nosso núcleo de colaborador com um receiver FastAPI simples (validar, deduplicar por id, mapear DE/PARA). É a opção mais madura tecnicamente; o custo (sem preço público) é o único risco a validar comercialmente.

**Correções do verificador:** Substância CONFIRMADA nas fontes primárias, com 3 correções. (1) DOWNLOAD DE DOCUMENTOS: o fluxo da API (developers.gupy.io/docs/fluxo-de-admissão-download-documentos) NÃO entrega .zip com PDF/JPEG + .TXT — ele entrega 'uma URL para cada documento que o pré-colaborador subiu', com expiração de 30s extensível até 12h (43200s) APENAS para documentos; URLs de CONTRATOS expiram em 30 minutos e 'Não é possível estender esse tempo' (o pesquisador disse expiração configurável até 12h de forma genérica). O pacote .zip com cópias PDF/JPEG + .TXT transcrito existe, mas é o download manual/em massa PELA PLATAFORMA, documentado na central de ajuda (suporte.gupy.io, artigo 'Download de Documentos no Gupy Admissão'), não na API — o pesquisador fundiu os dois mecanismos. (2) INTEGRAÇÕES PADRONIZADAS: a lista real no menu da doc é maior que a citada — RM TOTVS, Metadados, Sênior, ADP e Protheus (pesquisador citou só Metadados/Protheus/Sênior); Nasajon de fato NÃO aparece, isso está correto. (3) Detalhe menor: token é gerado em 'Setup > Tokens Generation' segundo a página de autenticação, não literalmente 'configurações avançadas'. TUDO O MAIS CONFIRMADO LITERALMENTE: POST /api/v1/webhooks com action='pre-employee.moved', postbackUrl, techOwnerName/Email, clientHeaders (com pegadinha real documentada: setar clientHeaders remove o Content-Type padrão); exigência literal 'No momento de gerar o token habilite os seguintes endpoints da V1: Webhook Configurations'; filtro por body.data.admission.status; at-least-once literal ('A Gupy garante pelo menos uma entrega... use a propriedade id para identificar duplicatas'); disparo 'toda vez que uma pessoa pré-colaboradora é movida entre etapas'; payload com candidate.name/email/mobileNumber/birthdate, job.code/department/role/branch, admission.documents.preEmployee (RG, CPF, CNH, dados bancários, Dependentes v2); status SEND_DOCUMENTS/SIGNING_CONTRACT/ADMISSION_CONCLUDED/OUT_PROCESS presentes na doc; disclaimer literal 'a integração NÃO GARANTE que TODOS os dados enviados serão os necessários para concluir uma admissão no sistema de folha'; teste com CPF/PIS/RG válidos; llms.txt + OpenAPI anunciados na home; API Reference lista Applications, Jobs, Career Pages, Departments, Job Custom Fields, Job Templates, Job Roles, Company Users, Branches, Post Hiring e Webhook Configurations. eSocial: busca site:developers.gupy.io não retorna nenhuma página sobre eSocial — ausência confirmada. PREÇO: gupy.io/precos existe mas sem nenhum valor numérico (só 'Solicitar demonstração' por plano; R&S e Admissão são linhas de produto separadas com tiers próprios — Professional/Premium/Premium Plus na Admissão) — 'sem preço público' confirmado. O R$730/mês está de fato na Betterteam ('planos que iniciam em R$ 730,00 mensais, com contrato anual'), mas outras fontes terciárias citam R$900 e até R$2mil/mês — número de baixa confiabilidade, tratar apenas como ordem de grandeza.

**Fontes:** <https://developers.gupy.io/> · <https://developers.gupy.io/docs/fluxo-de-admiss%C3%A3o-para-sistema-de-folha-> · <https://developers.gupy.io/docs/pre-employee-moved-event-1> · <https://developers.gupy.io/docs/produto-gupy-admiss%C3%A3o> · <https://developers.gupy.io/reference/intro/getting-started> · <https://developers.gupy.io/docs/fluxo-de-admiss%C3%A3o-download-documentos-de-admissao> · <https://www.betterteam.com/br/gupy (preço - fonte terciária, não confirmada)>

### Acesso RH / Unico People (Unico) — veredito: incorporar · verificação: confirmado

**O que faz:** Plataforma de admissão digital pura (não é ATS): RH abre uma 'posição' para o candidato, que envia documentos pelo celular; a Unico valida a documentação (SLA de 3h divulgado), colhe assinatura eletrônica do contrato e devolve o dossiê pronto para a folha. Marketing oficial: +60.000 admissões/mês, redução de até 90% no tempo de admissão.

**API:** SIM, pública (acessorh.gitbook.io). REST/JSON, base https://api.acessorh.com.br. Autenticação OAuth2 com SERVICE ACCOUNT da plataforma de identidade da Unico (acesso-io.github.io/docs .../oauth2) gerando Bearer token — modelo mais maduro que token fixo. v2 documenta: POST /v2/positions (cria a posição/admissão: role, department, unitID, pagamento com tipo de vínculo e salário, profile do candidato com nome/email/celular, flags sendSMS/sendEmail, campos opcionais como data de admissão, centro de custo, PCD, exame médico, documentos adicionais, benefícios) e POST /v2/positions/export (exporta posições concluídas por filtros — status, período de admissão, paginação — em formato definido por TEMPLATE: csv, txt, xml — é o mecanismo clássico de handoff para folha/ERP). GET /v2/organization traz organização > grupos > empresas com CNPJ. Na v1 há GET /v1/positions retornando JSON estruturado com candidatos, documentos e status. Cobre admissão de ponta a ponta; NÃO cobre vagas/candidatos de recrutamento (não é o escopo do produto).

**Webhooks:** SIM, documentados: position-created, position-archived e position-completed (este último dispara quando a admissão conclui — o gatilho para puxar o dossiê via GET/export e criar o colaborador no nosso núcleo). Retry automático a cada 5 segundos por até 3 dias antes de abandonar a entrega.

**Preço:** Sem preço público (site oferece 'calculadora de custo por admissão' e venda consultiva).

**LGPD/eSocial:** É a única das três cuja API expõe validação eSocial explícita: a resposta de posição concluída traz 'validations: esocial: approved'. Marketing oficial afirma conformidade LGPD e processos 'integrados ao eSocial'. Como valida documentos e biometria, é forte em compliance documental; ainda assim o payload/dossiê contém dados pessoais e documentos — DPA obrigatório.

**Justificativa do veredito:** Se o objetivo é admissão digital com validação documental terceirizada (sem trocar de ATS), o fluxo fecha: nosso sistema cria a posição via POST /v2/positions, o candidato faz tudo digital, o webhook position-completed avisa, e puxamos o dossiê via /v1/positions ou /v2/positions/export para criar o colaborador. Validação eSocial nativa na resposta é diferencial direto para o DP/Nasajon. Concorre com o Gupy Admissão — escolher UM dos dois para o módulo de admissão; Unico faz sentido se não quisermos contratar o ATS da Gupy junto.

**Correções do verificador:** Núcleo técnico integralmente confirmado nas fontes primárias (GitBook). Notas menores: (1) o campo de validação eSocial na resposta de Get Position é 'validation': { 'esocial': { 'approved': false } } — singular 'validation', não 'validations', e o exemplo da doc mostra approved:false (o campo existe e valida eSocial, como afirmado). (2) A página de ativação confirma 'Para a utilização da API é necessária uma conta de serviço' com link literal para acesso-io.github.io/docs/platform/identity/protocols/oauth2 — OAuth2 service account confirmado; a expressão 'Bearer token' não aparece literalmente na página de ativação (aparece na doc OAuth2 referenciada). (3) No exemplo de export, o template mostrado é 'csv-v2.2'; o mecanismo de template está confirmado, mas os formatos txt/xml não apareceram literalmente nos trechos que li. (4) A página de marketing unico.io/unicopeople/unico-people/ retornou HTTP 403 ao fetch direto (bloqueio de bot) — os claims de marketing (+60.000 admissões/mês, SLA de 3h — na verdade '90% das análises em até 3 horas úteis', validação eSocial) foram corroborados via outras páginas oficiais da Unico indexadas, mas não li a página exata ao vivo. Confirmado literalmente: webhooks 'position-created', 'position-archived', 'position-completed'; retry literal 'nova tentativa a cada 5 segundos por 3 dias (quando a requisição será abandonada)'; POST /v2/positions com role/department/unitID/pagamento(vinculo, valor, recorrencia)/profile(name, email, mobile)/sendSMS/sendEmail/admissionDate/costCenter/deficiencia/docs/benefícios; POST /v2/positions/export com filtros de status e dates.admissionDate; GET https://api.acessorh.com.br/v2/organization ('Lista todos os grupos e empresas da organização', com cnpj em customFields — no exemplo o valor é null); GET /v1/positions e detalhe com persons/documents/status. Base URL api.acessorh.com.br confirmada nos exemplos da doc. Sem preço público confirmado (existe calculadora de custo por admissão em unico.io, sem valores).

**Fontes:** <https://acessorh.gitbook.io/project/v2/api> · <https://acessorh.gitbook.io/project/v2/api/ativacao-da-api.md> · <https://acessorh.gitbook.io/project/v2/api/posicoes.md> · <https://acessorh.gitbook.io/project/v2/api/organizacao.md> · <https://acessorh.gitbook.io/project/llms-full.txt (webhooks position-*, OAuth2 service account, GET /v1/positions, validação eSocial)> · <https://unico.io/unicopeople/unico-people/ (marketing: LGPD, eSocial, SLA 3h)>

### Abler (ATS) — veredito: referencia · verificação: confirmado

**O que faz:** ATS brasileiro (forte em consultorias de R&S e recrutamento de volume): vagas, pipeline de candidatos, página de carreiras, banco de talentos (8M+), testes DISC/BigFive, hunting com IA. Tem uma etapa de 'admissão' no pipeline, mas é uma ficha estendida do candidato — não é admissão digital completa com validação documental como Gupy Admissão ou Unico People.

**API:** SIM, pública em https://developers.abler.com.br/ (ReDoc/OpenAPI, li o conteúdo completo). REST/JSON, base https://api.abler.com.br/v1. Autenticação: Bearer token FIXO gerado na plataforma (Configurações > Empresa > Integrações), enviado em Authorization; a própria doc avisa que o token NÃO EXPIRA e deve ir para um secrets manager. Endpoints: /customers (CRUD de clientes, com CNPJ — útil para nossos 5 CNPJs se usado no modelo consultoria), /vacancies (GET/POST/PATCH/DELETE, com vacancy_admission_info: salário, regime de contratação, centro de custo), /vacancies/{id}/candidates (listar candidatos da vaga e inserir candidato), /subscriptions (CRUD de inscrições de webhook) e /collections + /enums de apoio (cidades, estados, benefícios, regimes de contratação, times, usuários). IMPORTANTE: segundo a página oficial de planos, o acesso à API pública só existe nos planos Advanced e Elite.

**Webhooks:** SIM, documentados com payload completo: vacancy_created, vacancy_updated, vacancy_published, vacancy_deleted, candidate_hired e admission_finished. candidate_hired entrega candidate_name/cpf/email/cell_phone/pis/birthday, salário, contracting_regime, initial_date, cost_center, jornada, benefícios e dados do customer (CNPJ). admission_finished entrega a ficha completa: cpf, pis, cnh, nascimento, endereço/CEP, gênero, etnia, orientação sexual, deficiência, pretensão salarial, URL de PDF do currículo (a doc manda salvar o arquivo no nosso servidor). Registro self-service via POST /subscriptions.

**Preço:** Parcialmente público em https://abler.com.br/planos-e-precos: Essencial a partir de R$500/mês (até 5 vagas/mês, 50 avaliações); Pro, Advanced e Elite sem preço público (consultar vendas). API pública apenas em Advanced e Elite — ou seja, o preço do cenário com API não é público.

**LGPD/eSocial:** A documentação da API não menciona LGPD nem eSocial (verificado por busca no texto completo). Os payloads de admission_finished carregam dados SENSÍVEIS pela LGPD (etnia, orientação sexual, deficiência) — recebê-los exige base legal e cuidado extra no nosso lado. Token sem expiração é um ponto fraco de segurança operacional. Nada de validação documental/eSocial: o dossiê para o DP continuaria sendo montado por nós.

**Justificativa do veredito:** API real, aberta e com os webhooks certos (candidate_hired/admission_finished dariam para alimentar nosso núcleo de colaborador), e o único preço de entrada público da categoria. Mas: admissão rasa (sem validação documental nem eSocial), dados sensíveis no payload, token que não expira e API restrita a planos Advanced/Elite sem preço público. Vale como referência/plano B barato de ATS integrável — não como base do nosso módulo de admissão.

**Correções do verificador:** Nenhuma correção de substância — verificação forte: baixei a página completa da doc (1,9 MB, ReDoc/OpenAPI embutido) e inspecionei o texto bruto localmente, pois o fetch normal trunca. Confirmado literalmente no spec: base 'https://api.abler.com.br/v1' (33 ocorrências); aviso do token exatamente como citado: 'ATENÇÃO: Este token não expira. Insira-o em um lugar seguro dentro da aplicação, tais como gerenciadores de secrets ou arquivos .env. Não insira o token diretamente em seu código-fonte.'; geração do token via 'Configurações' na plataforma (no novo ATS, via 'Empresa') — bate com 'Configurações > Empresa > Integrações' em essência; endpoints /customers, /subscriptions, /collections, /enums e /vacancies com vacancy_admission_info todos presentes; todos os 6 webhooks presentes: vacancy_created, vacancy_updated, vacancy_published, vacancy_deleted, candidate_hired, admission_finished; payload com candidate_cpf, candidate_pis, candidate_name, candidate_email, candidate_cell_phone, candidate_birthday, customer_cnpj, contracting_regime, cost_center, initial_date — todos encontrados; campos sensíveis ethnicity, sexual_orientation e disability presentes (múltiplas ocorrências, incluindo no payload de admissão); campo do currículo literal: 'pdf': 'Arquivo PDF (URL com o arquivo, salvar o arquivo no seu servidor)'. Ausência de LGPD e eSocial confirmada: zero ocorrências de ambos os termos no texto completo da doc — exatamente como o pesquisador afirmou. Preços confirmados ao vivo em abler.com.br/planos-e-precos: Essencial 'A PARTIR DE R$ 500/mês' com 'Até 05 vagas/mês' e 50 avaliações; Pro e Advanced 'Consulte valores com o time de vendas', Elite 'Orçamento Personalizado'; 'Acesso a API pública' marcado apenas em Advanced e Elite. Única ressalva: help.abler.com.br não foi re-verificado individualmente (fonte redundante — os passos do token estão na própria doc de developers).

**Fontes:** <https://developers.abler.com.br/ (conteúdo OpenAPI completo baixado e inspecionado em 2026-07-24)> · <https://abler.com.br/planos-e-precos/> · <https://help.abler.com.br/ (primeiros passos da integração/token)>

**Notas do pesquisador:** Achados transversais da categoria: (1) As três ferramentas têm webhook documentado para o evento 'admitido' — o padrão de integração é idêntico ao nosso desenho: endpoint receiver no FastAPI (ou n8n como middleware) recebendo POST, com deduplicação (Gupy é explicitamente at-least-once) e resposta 200 rápida (Abler e Acesso RH fazem retry agressivo — Acesso RH tenta a cada 5s por 3 dias). (2) Nenhuma das três publica preço completo; só Abler (Essencial R$500/mês, sem API) e, por fonte terciária, Gupy (~R$730/mês) têm número público — orçamento da categoria exige contato comercial. (3) Divisão clara de papéis: Gupy = ATS + admissão digital completa (melhor doc de integração com folha do mercado, mas Nasajon NÃO está entre as integrações padronizadas — seria via webhook custom nosso, o que na prática nos convém pois o alvo é o nosso sistema, não a Nasajon direto); Unico People = só admissão digital, com validação documental terceirizada e flag eSocial na API; Abler = só ATS. (4) Decisão-chave para o nosso módulo de admissão: Gupy Admissão e Unico People são mutuamente excludentes — se contratarmos Gupy R&S, faz sentido o combo Gupy; se mantivermos recrutamento fora da Gupy, Unico People cobre a admissão sozinha. (5) LGPD: todos os payloads de admissão carregam documentos e dados sensíveis (Abler inclusive etnia/orientação sexual/deficiência); qualquer integração exige DPA com o fornecedor, criptografia em repouso no nosso PostgreSQL e política de retenção. (6) Autenticação: Acesso RH é o mais maduro (OAuth2 service account), Gupy usa Bearer token com escopos gerado na plataforma, Abler usa token estático sem expiração (guardar em secrets manager). (7) Todas expõem doc legível por máquina (Gupy: llms.txt + OpenAPI; Acesso RH: GitBook .md/llms-full.txt; Abler: ReDoc/OpenAPI), o que facilita gerar clients tipados para o nosso backend.

**Resumo do verificador:** Verificação adversarial concluída com leitura ao vivo das fontes primárias. ABLER: confirmado integralmente — baixei o OpenAPI/ReDoc completo (1,9 MB) e todos os endpoints, webhooks (candidate_hired/admission_finished), campos sensíveis, o aviso literal do token que não expira, a ausência total de LGPD/eSocial na doc e os preços (Essencial R$500/mês; API só em Advanced/Elite) batem exatamente. ACESSO RH/UNICO: confirmado — POST /v2/positions, export por template, GET /v2/organization (base api.acessorh.com.br), webhooks position-created/archived/completed com retry literal de 5s por 3 dias, OAuth2 service account e validação eSocial na resposta (campo real: 'validation.esocial.approved', singular) todos verificados no GitBook; única ressalva é que a página de marketing da Unico bloqueou fetch direto (403) — claims de 60 mil admissões/mês e SLA 3h corroborados por outras páginas oficiais. GUPY: parcial — todo o fluxo de integração afirmado existe e foi confirmado literalmente (webhook pre-employee.moved com permissão 'Webhook Configurations' V1, at-least-once com dedup por id, payload completo com documentos, status SEND_DOCUMENTS/SIGNING_CONTRACT/ADMISSION_CONCLUDED/OUT_PROCESS, disclaimer de que a integração não garante dados completos para a folha, ausência de eSocial na doc, Nasajon fora da lista de integrações padronizadas, sem preço público), MAS o pesquisador fundiu dois mecanismos de download: o .zip com PDF/JPEG + .TXT transcrito é o download pela PLATAFORMA (central de ajuda), enquanto o fluxo da API entrega uma URL por documento — com expiração extensível até 12h só para documentos; URLs de contrato expiram em 30 minutos fixos e não são extensíveis. A lista de integrações padronizadas também é maior que a citada (inclui RM TOTVS e ADP). Correções não alteram os vereditos do pesquisador: o desenho webhook->middleware FastAPI->núcleo de colaborador é viável nas três ferramentas conforme descrito.

## SST / saúde ocupacional / eSocial SST

### SOC (soc.com.br - AGE Technologies) — veredito: incorporar · verificação: confirmado

**O que faz:** Líder de mercado em software de SST: PCMSO, PGR, ASO, prontuário, agendamento de exames, CIPA, EPI, e mensageria eSocial SST própria (gera o XML e transmite direto ao governo). É o sistema que a maioria das clínicas de medicina ocupacional do Brasil usa.

**API:** API real e verificada ao vivo em duas camadas. (1) Web Services SOC: SOAP 1.1 (document/literal) em https://ws1.soc.com.br/WSSoc/ - conferi dois WSDLs públicos e válidos: FuncionarioModelo2Ws (operação importacaoFuncionario, cadastro/atualização/transferência de funcionário, retorno retornoWsVo com status) e AgendamentoWs (incluirAgendamento/alterarAgendamento/excluirAgendamento, auth via identificacaoUsuarioWsVo com código empresa/responsável/usuário). Ou seja: o RH da Fast pode EMPURRAR cadastro de funcionário e agendamento de exame para o SOC via SOAP. (2) Exporta Dados: endpoint HTTP (https://ws1.soc.com.br/WebSoc/exportadados) que recebe parâmetro JSON (código empresa + código do exporta dados + chave + tipoSaida) e devolve TXT/CSV/XML/HTML/JSON; autenticação por chave exclusiva por layout + trava de IP. A página oficial confirma layouts de 'Eventos do eSocial' e 'Relatório de Inconsistências do eSocial S-2210, S-2220, S-2221 e S-2230' e afastamentos pendentes de envio - ou seja, dá para PUXAR status/recibos/pendências do eSocial SST via API. A doc detalhada dos layouts fica dentro do próprio SOC (login de cliente); não há portal público de desenvolvedor (ajuda.soc.com.br não resolve; listagem de /WSSoc retorna 403), mas os WSDLs são públicos e funcionais. Docs de terceiros (WK Radar) confirmam que o SOC também entrega os XMLs S-2210/S-2220/S-2221/S-2240/S-3000 via web service para mensageria externa transmitir.

**Webhooks:** Sem webhook documentado publicamente. O Exporta Dados lista 'POST' como formato de saída (sugere push HTTP configurável), mas não há doc pública detalhando; na prática o padrão de mercado é pull (polling) no endpoint exportadados - encaixa bem num job do n8n.

**Preço:** Sem preço público. Modelo comercial via contato; relatos de mercado indicam cobrança por consumo/créditos no Exporta Dados, mas nada publicado oficialmente.

### Node nativo de WhatsApp do n8n (WhatsApp Business Cloud + WhatsApp Trigger) — veredito: incorporar · verificação: confirmado

**O que faz:** Integração pronta do n8n com a Cloud API da Meta. Node de ação: Send, Send Template, Send and Wait for Response (com botões de aprovação, texto livre ou formulário — útil para 'confirmar ciência do fechamento de ponto'), upload/download/delete de mídia. ## Open-source: BI / dashboards para people analytics

### Metabase (edição open-source) — veredito: referencia · verificação: confirmado

**O que faz:** Plataforma de BI self-service (perguntas, dashboards, query builder visual) que pode ser self-hosted. Oferece 3 vias de embedding: static/signed embedding (iframe com URL assinada por JWT), 'modular/interactive embedding' (SSO, drill-through, query builder dentro do app) e public links.

**API:** Documentação pública e boa. Static embedding (doc lida: metabase.com/docs/latest/embedding/static-embedding): o SEU backend assina uma URL com JWT (secret compartilhado) e renderiza em iframe — disponível na edição open-source GRATUITA, com banner 'Powered by Metabase' que só sai em plano pago. Limitações confirmadas na doc: static embed NÃO suporta row/column security nem drill-through; restrição de dados por usuário é feita via 'locked parameters' travados no token assinado pelo backend (funciona como RLS rudimentar controlado pelo seu FastAPI). Interactive/modular embedding com SSO, full-app embedding e o Embedded Analytics SDK exigem plano Pro/Enterprise (confirmado na doc de introdução ao embedding e no pricing). Ponto crítico lido na doc: na edição gratuita NÃO é possível desabilitar download/export de dados nos embeds — só Pro/Enterprise controlam isso.

**Webhooks:** Não avaliado em profundidade nesta pesquisa (não é o eixo da categoria); o produto tem alerts/assinaturas de dashboard, mas não li a doc específica de webhooks — tratar como não verificado.

**Preço:** Open source: gratuito, usuários ilimitados. Starter: US$ 100/mês (5 usuários, +US$ 6/usuário). Pro: US$ 575/mês (10 usuários, +US$ 12/usuário) — é o plano que libera embedding avançado/white-label. Enterprise: a partir de US$ 20.000/ano. Fonte: página pública de pricing lida ao vivo.

**LGPD/eSocial:** Self-hosted: dados ficam na sua infra (positivo para LGPD). Porém, para dado sensível de RH: (1) embeds estáticos gratuitos permitem download/export sem opção de desligar; (2) sem row/column security no static embed — a segregação depende inteiramente de locked parameters bem implementados no seu backend. Licença AGPL na edição OSS (confirmado em metabase.com/license): para embedar, a página oficial dá 3 opções — cumprir a AGPL, usar a Embedding License mantendo o logo, ou comprar licença comercial. Para uso interno por funcionários o risco de AGPL é baixo, mas existe. eSocial: não se aplica (é BI, não folha).

**Justificativa do veredito:** Dá para embedar de graça (static embedding com JWT + locked parameters), mas com três atritos para o caso de uso 'dado sensível de RH dentro do nosso front': banner obrigatório, impossibilidade de bloquear export de dados na edição gratuita e ausência de row-level security real no static embed. O embedding interativo de verdade custa US$ 575/mês. Útil como referência de UX e eventualmente como ferramenta interna de exploração do time de dados, mas não como componente de embedding do portal.

**Correções do verificador:** Nada errado de substância. Duas notas de precisão: (1) a alegação crítica 'não dá para desabilitar download/export na edição gratuita' está documentada em outra página que não a citada — metabase.com/docs/latest/embedding/static-embedding-parameters, que diz literalmente 'Disabling downloads is only available on Pro and Enterprise plans' (valores do parâmetro downloads: false/results/pdf) — a afirmação é verdadeira, só a fonte exata faltou na lista. (2) Terminologia: o Metabase reorganizou a doc — o que era 'static embedding' agora também aparece como 'guest embeds' dentro do guarda-chuva 'modular embedding'; guest embeds (URL assinada por JWT) funcionam em todos os planos inclusive OSS (com badge), e o que exige Pro/Enterprise é o modular embedding com SSO (drill-through, query builder, dados por usuário) — exatamente o que o pesquisador afirmou, com nomes ligeiramente diferentes. Todo o resto bateu literalmente: 'You can't use static embeds with row and column security, drill-through, and user-specific data'; banner removível só em Pro/Enterprise; restrição por locked parameters; pricing público Starter US$100/mês (5 usuários, +US$6), Pro US$575/mês (10 usuários, +US$12, whitelabel), Enterprise a partir de US$20.000/ano; licença AGPL com as 3 opções de embedding (cumprir AGPL / Embedding License mantendo o logo / licença comercial).

**Fontes:** <https://www.metabase.com/docs/latest/embedding/introduction> · <https://www.metabase.com/docs/latest/embedding/static-embedding> · <https://www.metabase.com/license/> · <https://www.metabase.com/pricing/>

### Apache Superset — veredito: exigir-prova-tecnica · verificação: confirmado

**O que faz:** Plataforma de BI open-source da Apache Software Foundation (dashboards, SQL Lab, charts) com suporte oficial a embedded dashboards via SDK JavaScript.

**API:** Documentação oficial lida (superset.apache.org/user-docs/using-superset/embedding/): fluxo 100% open-source — (1) habilitar feature flag EMBEDDED_SUPERSET; (2) seu backend (FastAPI) chama POST /api/v1/security/guest_token/ com service account e gera um guest token — nunca client-side; (3) o front usa o pacote npm @superset-ui/embedded-sdk para montar o dashboard; (4) regras de Row-Level Security podem ser passadas NO PAYLOAD do guest token, ou seja, o seu RBAC decide o que cada usuário vê (ex.: filtrar por CNPJ/unidade); (5) tokens expiram (GUEST_TOKEN_JWT_EXP_SECONDS, padrão 5 min) e há allowlist de domínios validando o Referer. Nenhuma parte do embedding é paga.

**Webhooks:** Não é o eixo da categoria; Superset tem 'Alerts & Reports' (e-mail/Slack) mas a doc específica não foi lida nesta pesquisa — não verificado.

**Preço:** Gratuito integralmente — licença Apache 2.0, projeto da Apache Software Foundation, sem edição enterprise (confirmado na doc: 'Licensed under the Apache License'; nenhuma funcionalidade de embedding é paga).

**LGPD/eSocial:** Self-hosted, dados na sua infra e RLS ditada pelo seu backend a cada token — o melhor alinhamento LGPD entre as opções de embedding sem custo: a segregação por perfil/unidade fica sob controle do seu RBAC, com tokens de vida curta. Licença Apache 2.0 sem risco de contaminação. Contrapartida operacional: é um sistema Python/Flask completo para operar (metadados próprios, cache, workers async para thumbnails/alerts). eSocial: não se aplica.

**Justificativa do veredito:** É a ÚNICA das quatro que entrega embedding completo com row-level security sem nenhum plano pago e com licença permissiva (Apache 2.0). Se a decisão for 'usar BI pronto embedado', é o Superset. Mas exige PoC antes de comprometer: avaliar o custo de operar um segundo sistema (deploy, upgrades, Redis/workers), a latência do fluxo guest-token e o quanto o iframe destoa do design system. A PoC deve comparar diretamente com a alternativa de dashboards nativos em React (ver notas).

**Fontes:** <https://superset.apache.org/user-docs/using-superset/embedding/> · <https://www.npmjs.com/package/@superset-ui/embedded-sdk> · <https://github.com/apache/superset/blob/master/superset-embedded-sdk/README.md>

### Lightdash — veredito: ignorar · verificação: confirmado

**O que faz:** BI dev-friendly acoplado ao dbt (métricas definidas no repositório dbt), com embedding via URL compartilhável, iframe com JWT e React SDK para Next.js.

**API:** Doc de embedding pública e lida (docs.lightdash.com/references/embedding): JWT gerado no backend, iframe e React SDK — arquitetura tecnicamente atraente para um front Next.js. PORÉM, a própria doc afirma: 'Embedding is available to all Lightdash Cloud users and Enterprise On-Prem customers' — ou seja, o embedding NÃO está na versão open-source self-hosted gratuita. As variáveis EMBED_ALLOW_ALL_DASHBOARDS_BY_DEFAULT / EMBED_ALLOW_ALL_CHARTS_BY_DEFAULT citadas na doc aplicam-se a deployments Enterprise On-Prem. A licença do repositório é MIT com exceção explícita: tudo sob packages/backend/src/ee tem licença comercial própria (lido no LICENSE do GitHub).

**Webhooks:** Não avaliado — irrelevante para o veredito, já que o recurso central (embedding) é pago.

**Preço:** Self-host do core: gratuito (MIT). Embedding: restrito a Cloud e Enterprise On-Prem; preço desses planos não é público nas fontes lidas — sem preço público verificado.

**LGPD/eSocial:** Core self-hosted manteria dados na infra própria, mas como o embedding exige plano pago (Cloud ou Enterprise), o cenário 'dado de RH embedado sem custo' não existe aqui. Exige também adotar dbt como camada de métricas — investimento adicional. eSocial: não se aplica.

**Justificativa do veredito:** O requisito central da categoria (embedding no front próprio sem plano pago) é exatamente o que o Lightdash coloca atrás do paywall (Cloud/Enterprise). Além disso, pressupõe dbt, que a stack atual não usa. Descartar para este fim; só reconsiderar se um dia a empresa adotar dbt E aceitar pagar Cloud.

**Fontes:** <https://docs.lightdash.com/references/embedding> · <https://raw.githubusercontent.com/lightdash/lightdash/main/LICENSE> · <https://github.com/lightdash/lightdash>

### Evidence — veredito: referencia · verificação: confirmado

**O que faz:** Framework 'BI as code' (MIT): páginas em Markdown + SQL que viram um SITE ESTÁTICO no build — queries rodam em build time, não por visita. Ideal para relatórios narrativos versionados em git.

**API:** Doc de deployment lida (docs.evidence.dev/deployment/overview): gera site estático; self-host em Netlify, Vercel, Cloudflare Pages, GitHub Pages, IIS, infra própria etc. Não há 'API de embedding' nem mecanismo nativo de autorização por usuário: a doc não descreve autenticação de usuário final no self-host além de proteções da plataforma de hospedagem (ex.: Cloudflare Access, senha global no Amplify). Framework MIT confirmado no repositório GitHub ('Evidence is licensed under the MIT license').

**Webhooks:** Não possui no framework open-source (site estático); rebuild de dados é feito por CI/CD (ex.: GitHub Actions) — conforme docs de deployment lidas.

**Preço:** Framework: gratuito (MIT). Evidence Cloud/Studio existe como oferta gerenciada, mas preço não foi verificado em fonte primária nesta pesquisa — sem preço público confirmado.

**LGPD/eSocial:** Ponto de atenção grave para RH: como as queries rodam no BUILD, os dados ficam embutidos nos arquivos estáticos publicados — qualquer pessoa com acesso ao site vê tudo; não há row-level security por usuário. Para dado sensível de pessoas, só serviria atrás do auth do portal e com dados já agregados/anonimizados. eSocial: não se aplica.

**Justificativa do veredito:** Não resolve o caso de uso principal (dashboard por usuário com RBAC dentro do app) por ser estático e sem autorização por linha/usuário. Mas é uma referência excelente e de custo zero para um subcaso real: relatórios mensais fechados de people analytics (ex.: 'Relatório de Turnover Q3' agregado por unidade), versionados em git e servidos atrás do auth existente.

**Correções do verificador:** Detalhe menor: os exemplos 'Cloudflare Access' e 'senha global no Amplify' não aparecem na página de overview de deployment lida (devem estar nas subpáginas por plataforma); o ponto central — a doc NÃO descreve autenticação de usuário final nativa no self-host — se confirma pela ausência. Nada de substância a corrigir.

**Fontes:** <https://docs.evidence.dev/deployment/overview> · <https://github.com/evidence-dev/evidence> · <https://docs.evidence.dev/deployment/self-host>

**Notas do pesquisador:** Resposta à pergunta-chave: para dashboards de RH DENTRO do front com RBAC próprio e sem plano pago, só existem duas rotas honestas — (1) Apache Superset embedded (única opção open-source com embedding completo + row-level security gratuita; Apache 2.0; guest token gerado pelo seu FastAPI carregando as regras RLS) e (2) construir nativo em React. Metabase gratuito embeda, mas com banner, sem RLS real no static embed e SEM conseguir bloquear export de dados (inaceitável para dado sensível de pessoas); o embedding decente custa US$ 575/mês. Lightdash cobra pelo embedding. Evidence é estático (dados embutidos no build, sem autorização por usuário). RECOMENDAÇÃO para o contexto Fast (3 devs, design system pronto, dados já no PostgreSQL próprio, KPIs de RH previsíveis — headcount, turnover, absenteísmo, custo de folha por CNPJ/unidade): construir os dashboards NATIVOS em React (Recharts/ECharts/visx) sobre endpoints FastAPI agregados com o RBAC existente tende a ser o melhor custo-benefício: zero sistema extra para operar, RBAC uniforme, UX 100% no design system, sem iframe. O argumento contra o nativo — 'BI pronto dá exploração self-service' — só pesa se o RH realmente for montar consultas ad-hoc; se essa demanda se confirmar, rodar a PoC do Superset (embedding gratuito) antes de qualquer decisão de compra. Nota transversal LGPD: todas as opções self-hosted mantêm dados na infra própria, mas o vetor de risco em BI de RH é exportação/downloads e granularidade de acesso — o desenho nativo (agregação no backend, mínimo necessário por perfil) é o que dá controle mais fino. Método: todas as afirmações acima vêm de páginas oficiais lidas ao vivo em 2026-07-24 (docs e pricing do Metabase, docs de embedding do Superset, doc de embedding e LICENSE do Lightdash, docs de deployment e repositório do Evidence); preços de Lightdash Cloud e Evidence Cloud não são públicos nas fontes consultadas.

**Resumo do verificador:** Verificação adversarial concluída em 2026-07-24 relendo todas as fontes primárias: os 4 achados foram CONFIRMADOS, sem nenhuma refutação. O pesquisador foi preciso e honesto, inclusive nos achados negativos. Pontos críticos revalidados ao vivo: (1) Metabase OSS embeda de graça via JWT, mas com banner obrigatório, sem row/column security nem drill-through no embed estático ('You can't use static embeds with row and column security, drill-through, and user-specific data') e SEM poder desabilitar download/export ('Disabling downloads is only available on Pro and Enterprise plans') — preços públicos conferem (Pro US$575/mês, Enterprise a partir de US$20.000/ano) e a licença é AGPL com 3 vias de embedding; única correção é de fonte/terminologia, não de substância. (2) Superset é de fato a única das quatro com embedding completo gratuito: feature flag EMBEDDED_SUPERSET, guest token gerado pelo backend com regras RLS no payload, expiração default de 5 min e allowlist de domínios — tudo literal na doc oficial, sem qualquer recurso pago. (3) Lightdash confirmadamente restringe embedding a Cloud/Enterprise On-Prem (frase literal na doc) e a licença MIT tem exceção comercial para packages/backend/src/ee — veredito 'ignorar' sustentado. (4) Evidence é site estático com queries em build time e sem autenticação por usuário na doc, MIT — adequado só para relatórios agregados atrás do auth do portal. As NOTAS DO PESQUISADOR (Superset embedded ou dashboards nativos em React como únicas rotas sem custo com RBAC próprio; recomendação de nativo para o contexto Fast) decorrem corretamente das evidências verificadas.
